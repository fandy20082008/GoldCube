# GoldCube 持续二开、开源与商业运营管理规范

版本：1.0｜制定日期：2026-09-22｜适用项目：基于 VOZEB-PRO 的 GoldCube 前端、后端、Worker、部署工具、文档及分发制品。

本文件供项目经理组织实施。它区分许可证要求与团队主动采取的管理措施，不替代对争议、历史违规或特殊授权的专业法律判断。制度交付不代表源码审计、公开发布、分支保护或 CI 已经完成。

## 一、项目决定与不可混淆的原则

第19方案的已批准范围优先于旧全祖先公开计划：两仓完整开发历史保留私有，公开完整发布源码快照作为新历史起点。AGPL对应源码及适用声明仍完整交付，不公开纯内部审计/私人记录或整个开发祖先。仅历史发现项与实际快照扫描分别处置，既有泄露及custom.12供源义务不因快照消失。内部工程完善项与影响实际交付的权利、秘密、源码完整性问题分开管理。

1. 项目采用“旧 AGPL 基线持续二开、项目自有代码完全开源、允许收费经营”的路线。后续独立开发不因上游换协议而当然受 BUSL 约束；必须持续履行旧版 AGPL，并核对第三方材料的权利。
2. 受旧版 AGPL 约束的作品继续按适用 AGPL 条款提供；团队自有且有权授权的项目代码统一采取兼容的开源方式。对第三方组件保留其原许可证，不能擅自把全部依赖重新标为 AGPL。对版本限定用语（only/or-later）需按原始授权核对，禁止自行扩大。
3. 本项目“完全开源”的内部政策覆盖本项目开发的前端、后端、Worker、配套构建和部署脚本及必要接口定义，不以拆目录、拆服务、改品牌为由隐藏项目代码。第三方 SaaS 的服务端实现不属于本项目可擅自公开的代码。
4. 完全开源不包括真实密钥、账户口令、用户数据、生产数据库、客户媒体、支付资料或私人运维记录；必要配置应提供安全模板。此处是保护数据，不是删去运行和构建所需的项目实现。
5. 收会员费、订阅费、积分或服务费本身不违反 AGPL；收费服务与免费获取对应源码可以并存。不得用网站条款、下载协议或 NDA 剥夺用户对受 AGPL 约束源码的修改、再分发等权利。
6. 当前上游的 BUSL 版本不因本项目愿意公开源码就自动获得商业使用许可。不能只保留旧 LICENSE，却把新版受限代码引入项目。

## 三、代码与材料来源规则

| 来源 | 默认处理 | 合并前必须有的记录 |
| --- | --- | --- |
| 固定旧 AGPL 基线 | 允许在协议条件下使用 | 完整 commit、历史许可、上游链接 |
| 团队在旧版上独立编写的代码 | 允许，走正常评审 | 需求、修改说明、作者/贡献权利确认 |
| 第三方开源依赖、示例、字体、图标、素材 | 逐项审查，固定版本 | URL、版本/commit、许可证、版权声明、兼容性及分发义务 |
| 上游改协议后的提交或代码片段 | 默认不导入；逐项隔离评估 | 精确文件/补丁来源及可用授权；仅日期晚不能证明每一行必然受 BUSL 独占限制 |
| 新版文件中与旧版完全相同的内容 | 优先直接从固定旧版取得 | 旧版中相同内容的可复核定位；不能顺带复制新版新增部分 |
| GitHub Issue/PR、群聊、博客中的补丁 | 不因公开可见而自动可用 | 发布者权利、明确许可或旧版来源证据 |
| 无来源归档、别人打包的镜像、匿名补丁 | 阻断引入 | 补齐来源和许可，否则自行实现或替换 |
| AI 生成或 AI 帮忙移植的实现 | 仍由开发和评审人负责 | 输入材料来源、是否含外部代码、依赖和引用记录；不得标为“AI 写的所以无版权问题” |

禁止行为：直接 pull/merge/rebase 当前上游 main 进入业务分支；无来源审核的 cherry-pick、复制文件、套用补丁或升级到新版镜像；把受限代码翻译语言、改变量名或让 AI 改写后当成独立原创。

允许只读查看许可、发布说明和安全公告。fetch 只会获取对象和引用，本身不改变业务授权基线；任何上游材料进入构建、运行或分发才必须完成来源审核。不得把删除远程引用或旧许可证文件当成消除已引入代码风险的方法。

## 四、每次二开的执行流程

### 1. 需求进入开发前

项目经理在任务单标记变更类型：独立开发 / 第三方引入 / 上游修复参考 / 部署制品变更。开发人员确认使用固定旧版基线，列明计划引用的外部材料。无需逐项请求原作者批准正常旧版开发；仅在确实需要新授权时走权利核实流程。

### 2. 编写和评审

- 在业务分支派生的功能分支开发；保留能追溯的提交，不为隐藏来源伪造作者、时间或历史。
- PR 说明必须填写来源声明。纯项目内修改可写“基于既有旧 AGPL 分支独立实现，无新增外部代码”，不要求给每行代码填表。
- 引入外部代码、资产或依赖时，填写来源台账并附准确版本；人工评审确认许可兼容性和权利声明。
- 架构变化须更新开源交付范围；不能只公开界面而隐藏项目配套后端和 Worker。
- 修改 LICENSE、版权声明、NOTICE、贡献者条款和基线记录时，必须进行专项评审；不得顺手覆盖为上游当前文件。
- 发现来源不清的材料时暂停该部分合并，可并行开发无关部分。项目经理的业务批准不能替代版权许可。

### 3. 发布与服务开放

以以下步骤作为团队强制发布政策：冻结干净的发布提交 → 构建与测试 → 生成源码包和第三方清单 → 完成秘密/个人数据检查 → 发布对应源码并验证获取入口 → 部署该提交构建的镜像 → 验证站点显示的版本和源码入口 → 归档发布证据。

源码提供与用户可访问的修改版服务同步，不能以“下周补开源”“月底合并”“尚未公测”为常规宽限。紧急修复也必须配套提供对应源码；不能用安全紧急为由自动免除义务。出现无法交付的情况时，停止新版本放量，必要时回滚到已合规交付的版本。

## 五、内测、公测与源码交付标准

AGPL 第 13 条要求修改版向通过网络交互的用户显著提供免费获取完整对应源码的机会，不以是否收费或是否宣布公测为触发条件。

- 单人本地研发一般不要求公开公共 GitHub；同一组织内部的网络使用需按具体关系处理，不能简单把“内网”当成条款豁免。
- 外部受邀用户、朋友、客户参加联网内测时，应向这些用户提供源码获取入口，不等待公测。
- 本项目选择公开仓库作为长期交付方式；GitHub 是管理选择，不是 AGPL 指定的平台。临时可用可靠源码下载站，但要保证相应用户免费获取且权利不受额外限制。
- 用户界面设置显著的“开源许可与源码”入口；链接到本产品的对应版本，不只链接原作者仓库、空仓库或浮动 main。
- 每次运行版本对应不可变 commit/tag 和可下载源码归档。源码须包含项目实际修改、构建与安装脚本、锁文件、必要配置模板及接口定义，不能只有编译产物或差异截图。
- 在隔离环境用公开材料完成构建或记录必要的外部依赖与配置步骤，防止公开材料缺失。一般工具、系统库等范围按 AGPL 定义处理，不要求分发第三方密钥或购买的服务账户。
- 保留原权利声明、AGPL 文本、第三方许可及免责声明，标记本项目修改及日期；自有品牌不代表可以冒充原作者官方，也不自动获得其商标许可。
- 保留历史已发布源码与版本映射，便于当前用户、下载者及审计追溯。具体分发渠道可能另有源码供给期限要求，单独核对；不要把团队的长期保留政策宣称为统一法定期限。

如已发生外部内测但未提供源码，及时补齐并保留真实整改记录。不得假定未来公测开源能自动消除过去的问题；需要时由法律顾问结合 AGPL 第 8 条评估终止及恢复规则。

## 六、项目经理发布门禁

下列任一项为“否”或“未知”，阻止该次新增发布；先解决问题，不自动认定整项目违法：

1. 发布版本来源可追溯，固定旧基线未被未经审核的新上游替换。
2. 新增外部代码/依赖/资产已登记并核对兼容授权，无已知来源不明材料。
3. 受保护许可和版权声明完整，项目自身开源范围符合既定承诺。
4. 源码与待运行制品一致，前端、后端和 Worker 均有对应版本。
5. 用户可免费取得对应源码，入口显著，下载内容经验证。
6. 必要构建材料齐全，秘密与个人数据检查通过。
7. PR、人工许可审查、质量验证、制品 digest 和回滚版本已记录。

一人项目也必须完成全部角色检查并记录，不能虚构第二位审核人。存在法律解释争议、第三方权利争议、商业授权范围冲突时，找具备相关能力的法律顾问核实。

## 七、自动化控制要求

由技术负责人落地以下检查，项目经理验收。规范和检查脚本不代表远端保护、源码下载或运行制品验收已完成：

- 在本项目主分支配置 PR 审查、必要检查及对许可/来源台账/发布流程的指定评审；CODEOWNERS 只有配合平台保护设置才形成实际约束。
- 私有开发来源检查校验完整旧基线身份、祖先关系、LICENSE预期内容和已知BUSL切换提交未进入开发历史。公开快照无旧祖先时不能简单跳过：`GOLDCUBE_SOURCE_MODE=public-snapshot` 必须提供仓外审核证明原始 JSON 及独立受控的 `GOLDCUBE_SNAPSHOT_PROOF_SHA256`；两仓分别核验本仓新根、HEAD/tree、规范成员、归档、许可和对仓 commit。私有模式仍运行原祖先检查；公开模式缺证或摘要不匹配直接失败。受控变量须由仓库负责人在保护设置中配置并核验，候选 PR 不得自行改写信任锚；代码接线不代表远端保护已启用或证明已签发。浅克隆、grafts、缺对象或命令异常不视为通过。
- Git 祖先检查只是辅助，不能识别人工复制、squash 或改写后引入的新版代码；来源台账与人工审查不可删除。
- 检查依赖锁定、许可证清单及源码交付清单变化；许可证扫描器只能提供线索，未知/多许可证选择由人工判断。
- 构建从干净提交产生不可变镜像标签并记录 digest；前后端若在不同仓库，发布清单记录各自 commit。禁止浮动 latest 冒充可追溯版本。
- 执行秘密扫描，验证公开源码下载、版本映射和署名入口。许可证检查失败即阻断发布，不允许直接 ignore 后当成合规通过。

原有升级流程若允许“任何新 tag 先合并到临时分支再测试”，须补上前置许可来源审核；测试通过不能证明新版本有商用或再分发权限。

## 八、新版功能、安全修复与授权例外

需要新版能力时按顺序处理：从旧版和独立需求自行实现；寻找授权兼容的第三方实现；或者就精确范围取得有效授权。

安全公告中的漏洞描述和测试现象可以用于定位旧版自身问题，不应直接照搬未核验授权的修复表达。已有人员接触受限代码时如来源难以分离，应进行专项评估；记录所谓“独立重写”并不能自动消除复制事实。

另行商业授权必须明确覆盖：使用主体、产品、版本、商业运行、修改、源码公开、再分发及项目计划采用的许可证。仅允许闭源自营的合同未必支持本项目完全开源路线。有效权利凭证及兼容性结论齐全后再引入；不能只凭付款、聊天一句“可以商用”或项目经理签字。

## 九、证据和贡献者管理

- 保留固定上游提交、旧版源码归档、历史许可/商业说明、文件哈希、二开历史和每次发布清单。可靠的第三方平台记录可作为时间佐证。
- 完整 .git 和源归档私密离线备份；不要为公开代码直接推送可能含秘密的全部历史。发现历史泄密先轮换凭据，再按安全流程处理，证据副本受控保存。
- 签名提交、哈希和可信时间戳的作用不同：哈希检测内容变化，普通 Git 日期不是可信时间证明，今天做的时间戳不能证明 8 月已下载。禁止补造证据。
- 在 README 中如实说明基于固定旧 AGPL 版本的独立二开；不得使用“原作者官方授权商业版”等无依据措辞。
- 明确员工、外包和社区贡献者对所交付代码的权利，以及按项目许可证贡献的同意。不要无条件复制上游 CLA 中授予上游维护者的特别权利到本项目，也不要把收到 PR 当成所有权完整核验。

## 十一、发现问题时

保留原始记录并定位受影响文件、提交、制品及使用者；暂停相关新增发布和导入；核实旧版来源或其他授权；必要时替换/独立实现、回滚服务或取得兼容授权；补齐应提供的源码；记录整改和复核。不要删除 LICENSE、重写历史或给未知代码换名字以掩盖来源问题。

项目经理不需要承诺“零法律风险”。验收目标是每次引入有来源、每次授权可解释、每次运行有对应源码、每次决定留有真实记录。
